# 开发记录

成品由 Cursor Cloud Agent（模型 Grok）在空仓库 `moshi-vuln-guard` 里实现。对开发者可见、并实际驱动这次实现的提示词，就是 [prompts/00-任务原文.md](prompts/00-任务原文.md)。没有另写一套隐藏的业务提示词，也没有把产品内部的系统指令抄进仓库。

运行时如果配置了语言模型，程序只读两份文本：

- [skills/remediation-advisor.md](skills/remediation-advisor.md)，作为系统消息
- [prompts/runtime-user.md](prompts/runtime-user.md)，作为用户消息，其中 `{facts}` 会被替换成方案事实 JSON

没有 `VULNGUARD_LLM_API_KEY` 时不会发网络请求，说明由 `vulnguard/advise.py` 的模板生成。样例报告走的是这条路径，数据源本身是在线的 OSV、KEV 和 EPSS。

## 实现时做过的决定

1. 语言选 Python。采集、版本比较、匹配和 Web 可以放在一个进程里，演示命令短。
2. 漏洞数据以 OSV 为主，中间件补上对照过公告的策展条目。OSV 的 `querybatch` 只返回编号，所以改用 `POST /v1/query` 拿完整记录。
3. CVE-2022-0543 只匹配 Debian 包版本。官方 Redis 镜像从源码构建，不套用这条打包缺陷。依据是 Debian 安全追踪：buster 修复于 `5:5.0.14-1+deb10u2`，bullseye 修复于 `5:6.0.16-1+deb11u2`。
4. nginx 的建议版本写成「不低于 1.20.1 的现行 stable」。1.21.0 虽然包含该 CVE 的修复，但在 2026 年不再适合当作升级目标。
5. 同一 CVE 的 GHSA 与 `GO-` 记录会合并。否则 `gopkg.in/yaml.v3` 的 CVE-2022-28948 会因为后一条没有 CVSS 向量而被显示成无分数。
6. 可执行命令与模型说明分开。白名单在生成时哈希，执行前再核对。大版本升级保持人工步骤。
7. 演示不安装有漏洞的旧依赖，只读取清单。旧的官方镜像写在 Compose 里，供有 Docker 的环境扫版本；本环境没有守护进程，样例报告来自 `demo/lab`。
8. 快照于 2026-11-03 从 OSV、KEV（目录 1766 条，与本次 CVE 相交的 3 条）和 EPSS 拉取，放在 `vulnguard/data/`，保证离线仍能复现。

## 关键迭代决策时间线

记录的是设计取舍，不是重放提示词。两次实现都由 Cursor Cloud Agent 完成，业务提示词就是仓库里的任务原文；没有另造多轮对话稿。

1. 首轮实现：用 Python 单进程把采集、匹配、报告和界面放在一起。OSV 改用 `POST /v1/query`，因为 `querybatch` 只返回编号。CVE-2022-0543 只匹配 Debian 包。可执行命令与模型说明分开，白名单在执行前核对摘要。本环境没有 Docker 守护进程，可复现样例放在 `demo/lab`。
2. 匹配打磨：同一 CVE 的 GHSA 与 `GO-` 记录合并，避免没有 CVSS 向量的那条把分数冲掉。nginx 的建议写成「不低于 1.20.1 的现行 stable」，而不是停在 1.21.0。修复版本取「每条公告的最低可用修复，再取能盖住全部条目的最大者」，Express 因此留在 4.20.0。
3. 交卷前补充：README 写明已知局限。rpm 与 apk 做成只读采集，命令不存在就跳过。Trivy JSON 作为第二意见附在报告中，不替换 OSV，也不进入可执行方案。本环境下载并运行了 Trivy 0.76.1，对 `demo/lab/app` 的输出在 `demo/trivy/live-fs.json`，与夹具合并后的报告在 `artifacts/trivy-live/`。二进制不进仓库；没有 `trivy` 时仍可读 `demo/lab/trivy.json`。
4. 样例与 Compose：`artifacts/demo-run` 按带 Trivy 第二意见的当前代码重新生成。日常 `vulnguard demo` 改写到 `runtime/reports/`，避免改到已提交样例。Compose 镜像安装 Docker 客户端并挂载套接字，`--source docker` 只扫带 `vulnguard.scan=true` 的旧容器，日志打印 `巡检来源=docker`。
